## 4. Blocks applied unnecessarily? — 4 concrete over-blocks

1. **Multi-`sed` batches false-fired (≥2 instances).** `sed -n '55,70p' f; sed -n '301,302p' f; rg …` blocked although AGENTS.md allows "sed -n when batching 2+ regions". Root cause `permission-gate.ts:575-580`: `sedBatch` counts ranges only **inside one sed invocation** (`;…p` or `-e`×2), not `;`-joined sed commands. Recovery cheap (2 parallel reads, one turn), but contradicts the documented rule.
2. **Whole-command veto for a trivial segment.** `date; cat .watermark.json (49 bytes); ls …` — entire status command blocked over a 49-byte cat; whole batch re-issued with `jq`. Overhead exceeded the "saved" bytes many times over.
3. **`curl -sL … | jq` blocked as Reading** — *corrected during fix implementation:* the block reason fired on a trailing `cat` segment (`not bash 'cat'`), not on the curl itself — pipes already exempt network fetches from R2. Root cause is the same whole-command veto as finding 2; covered by the trivial-cat fix below. The model still abandoned the lookup, so the veto cost remains real.
4. **Pure style enforcement, zero token delta.** `sed -n '15,22p' ~/.zshrc` blocked → `read offset 15 limit 8` returned identical bytes.

Plus 1 deliberate evasion (RETRY-SAME `git clone`+`git log`).

## 5. Bottom line

- Recovery behavior: excellent — 99% one-shot compliant, no thrashing, no revenge loops.
- Token ROI per block: negative on measurable numbers (~460 tok cost vs ~6–8K tok total measured savings over 2 days). The gate's value is preventive (big-file dumps, duplicate runs, context flooding) and diagnostic (Anchor Guard line hints), not per-block savings. Re-run is the one clearly positive-ROI family.
- Recommended fixes: count `;`-joined sed regions as a batch (match the documented rule); exempt trivially small `cat` segments in batched commands instead of vetoing the whole command; exclude `curl|jq` network fetches from the Reading rule.

## 6. Fixes applied — 2026-10-08

Implemented in `extensions/permission-gate.ts` (comment trail in-code, `tests/permission-gate.test.mjs` 69/69 green, `tsc --noEmit` clean):

1. **Distributed sed batch** — `sedViewers` counts `;`-joined `sed -n` viewers; `sedBatch` now passes when `sedViewers >= 2`. Rationale: AGENTS.md sanctions "batching 2+ regions"; per-invocation counting false-fired twice. Same dump ceiling as the already-sanctioned `-e`×2 form → no new evasion lane.
2. **Trivial batched cat** — `trivialCat()`: a `cat` of ≤128 bytes total inside a multi-segment command is exempt (standalone cats, flags, globs, or unstatable targets still block; resolution failure falls back to blocking). Rationale: a block costs ~460 tok measured; vetoing a whole command over a 49-byte dump is a net loss. Threshold 128 B ≈ 32 tok — an order of magnitude below block cost, so the exemption can never cost more than it saves.
3. **curl|jq** — no rule change needed (see corrected finding 3): R2 never fired on the fetch itself.
4. **Re-block escalation** (the audit's single RETRY-SAME case) — session trace showed the model re-sent the blocked `git clone + git log` **verbatim twice** (06:01:17 blocked → 06:01:20 identical re-send blocked with the same reason → compliant only on the 3rd attempt). Root cause: the second block repeated the original reason, giving no signal that the re-send itself was the mistake. Fix: `pendingBashFull`/`lastBlockedBash` state — a verbatim re-send of the just-blocked command within 2 min gets `Token Economy (Re-block): … that reason still applies. Change the command per it; a verbatim re-send only gets blocked again.` Real (non-gate) command failures don't arm it (family-prefix match, not isError alone); state clears on compact/session switch. Tests: verbatim re-send escalates, compliant variant passes, real failure doesn't arm — 72/72 green, `tsc --noEmit` clean, `block-recovery-audit` gate ≥85% still OK.
